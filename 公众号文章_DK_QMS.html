用 AI 审 GMP 文档是什么体验？我做了个本地小工具，还接上了自己的知识库

DK QMS · GMP 文档审核助手 · 2026-08-29

先讲个真实的场景。QA 要审一份偏差调查报告，手边摆着 GMP 附录、公司几百份 SOP、还有一堆历史案例。要在规定时限内把「根因分析是不是挖到底了」「CAPA 能不能落地验证」「数据完整性有没有踩 ALCOA+ 的红线」逐条核对完，还得在 Word 里留下可追溯的审阅意见。

这个活儿，干过的人都懂。翻标准翻到手酸是小事，最怕的是脑子里的条款跟文档里的表述对不上，批注写了一堆，回头自己也说不清依据在哪。

所以我把这个场景做成了一件趁手的本地小工具，名字叫 DK QMS。核心思路很简单，文档解析、AI 审核、批注导出全部在浏览器里完成，AI 审的时候不是凭记忆瞎说，而是真的去检索一个挂在本机的知识库来取证。今天把它的功能架构、用法和一段真实样例都摊开讲。

它到底能干什么

DK QMS 是一个 GMP 文档审核助手，导入一份 Word 或 PDF 报告，AI 会结合知识库自动审阅，最后导出一份带原生批注的新文档。支持的文档类型很宽，偏差调查报告、风险评估报告、SOP 标准操作规程都可以，只审内容，不动版式。

所有重活都在浏览器里跑，数据不出本机，密钥也永远留在服务端，这在制药场景里是刚需。

功能架构：纯静态 SPA + 极简代理

架构上我刻意做了减法。前端是一个纯静态 SPA，文档解析、三阶段审校编排、批注导出全部在浏览器内完成。服务端只有一个极简 Node 代理，职责就两条，转发 LLM 调用、转发知识库检索，顺便托管静态页面。

为什么这么设计？因为实测下来，模型 API 是支持浏览器跨域直连的，但本机知识库的 MCP 接口不带 CORS 头，浏览器直接被拦。所以知识库这一路必须走代理，LLM 也就一起走了，好处是密钥可以稳稳地留在服务端，浏览器永不接触明文。

关于模型的本地化，这里多说几句：这套工具从架构上就是「本地优先」的。文中出现的 DeepSeek 仅仅是我们做样例测试时临时接的外部模型，用来演示效果，不代表生产部署建议。如果要在企业里正式部署，强烈建议接入部署在本机的开源模型（例如通过 Ollama 或 LM Studio 运行的本地大模型）。一旦换成本地模型，模型、知识库、文档全程都在企业内网，文本不出本机、不出内网，从根源上杜绝数据丢失或泄露的可能性。以这个场景的审核任务量来看，本地模型的效果完全够用，而且越用越顺手。

灵魂：Linkly AI 知识库

这个项目最核心的部分，就是它挂了一个 Linkly AI 本机知识库。Linkly AI 把制药相关的验证文档、GMP 标准、本地案例全部索引进了知识库，通过 MCP 接口暴露检索能力。DK QMS 审文档的时候，不是让 AI 凭训练记忆瞎编条款，而是真的去知识库里检索对应标准，把条款和原文片段作为批注的依据。

说人话就是，AI 批注里写的每条「依据」，背后都有一条真实可查的检索结果，而不是模型自己脑补的。这对制药行业这种「批注要有出处」的场景，价值是决定性的。

三阶段审核流程

点一下「开始 AI 审核」，前端会按下面这套流程自动跑完，每一步都有进度反馈。

发送前脱敏
姓名、工号、手机、邮箱、身份证、批号、设备编号等敏感信息自动打码，原始文档和导出文件不受影响。
提炼关键问题
先判断文档类型（偏差 / 风险评估 / SOP / 其他），再按 GMP 六维框架生成 4–8 个针对性问题，每题绑定一个可检索的知识库 query。
检索知识库证据
逐题调用 Linkly AI 知识库 search，把命中的条款、文件名、相关度、原文片段整理成证据块。
生成结构化批注
综合原文、关键问题与知识库证据，输出锚定原文片段的批注，含严重度、问题类别、引用条款、修改建议、来源。
图 2 · 三阶段审核流程（脱敏 → 问题 → 取证 → 批注 → 导出）

审核维度方面，内置了一套 GMP 审核框架常量，覆盖六类维度：偏差管理、CAPA、风险评估（ICH Q9）、数据完整性（ALCOA+）、文件管理 / SOP、合规与可追溯。想调整「审核看哪些方面」，改这一处常量即可，第一、三阶段自动适配。

越用越聪明的经验教训库

这套工具还有一个很实用的特性，审核的内容是可以不断积累的。企业自己的历史偏差报告、已批准的风险评估、审核通过的 SOP，都可以持续加进知识库。今天审的每一份文档、每一条被验证有效的批注，都是明天审核的依据。

你可以把它想象成一个经验教训库，随着积累越来越厚，AI 的审核依据越来越广，能覆盖的条款越来越全，提出的问题也会越来越精准。用一段时间之后你会明显感觉到，它不再是泛泛的通用问答，而是一个真正长在公司体系里、只属于自己团队的审核助手。

双格式原生批注导出

审核结果不是简单的一段评语，而是可以写回原文档的原生批注。

Word 原生批注
导出为 OOXML 评论，在 Word / WPS 审阅窗格里可以逐条查看、接受、拒绝，完全符合现有的审核流转习惯。
PDF 高亮批注
在原始版式上叠加半透明高亮矩形，并写入原生 Highlight 注释，图片、表格、排版全部保留，阅读器审阅窗格可看。

隐私与安全设计

制药行业的文档敏感度高，这块我做了多重防线。一是文档全程本地处理，不上传任何云端；二是 API Key 只存在服务端配置文件，浏览器拿到的永远是掩码；三是发送给模型和知识库的文本先做脱敏，姓名、工号、批号、设备编号这些自动打码；四是如果接入的是本机部署的模型，从原文档、中间过程到导出文件，全程都不出企业内网，连出网请求都不会有。

脱敏这层值得单独说一句，它相当于在「本机处理」和「模型调用」之间再加一道隔离，是双保险。即使文档留在本机，发送出去给模型和知识库的文本也会先被打码，敏感信息只以脱敏形态出现，从机制上进一步压缩隐私泄露的可能。原始文件始终保持完整，只有模型和知识库看到的文本是脱敏后的。

说个开发时踩过的真实坑，AI 曾把「设备操作员」「生产主管」这类职位名误判成 [姓名] 占位符，追查了半天才发现是脱敏规则把职位词后的汉字当姓名打码了，修掉之后这类误判就彻底消失了。这种细节，正是这套工具和通用 AI 问答之间的差距所在。

使用方法

工具是本地单机部署，没有登录、没有云依赖，一条命令一条配置就能跑起来。前提是你本机装好了 Node.js 20+，并且启动了 Linkly AI 知识库服务。

# 1. 获取代码并安装依赖
git clone https://github.com/dreamke/DK-QMS.git
cd DK-QMS
npm install

# 2. 准备配置（填入模型 API Key 与知识库地址）
cp data/config.example.json data/config.json
# 编辑 data/config.json，填入模型 BaseURL / API Key / 模型名

# 3. 构建前端并启动
npm run build
npm start
# 浏览器打开 http://localhost:8787

也可以直接用开发模式，一条 npm run dev 同时起前端热更新和代理服务，前端在 5173 端口，代理在 8787 端口。首次进入先到「设置」页填好模型 API 和知识库地址，点「列举知识库」验证连通，然后就可以开始导文档审核了。

配置模型时提醒一句，如果是在企业内网部署，建议把模型的 Base URL 指向本地模型服务（例如 Ollama 或 LM Studio），而不是外网 API。示例里的 DeepSeek 只是演示用的外部模型，正式使用本地模型更稳、更安全。

做这个工具的过程里我最大的感受是，AI 在制药这种高合规行业里，价值不在「替代人」，而在「把人的时间从翻标准里解放出来」。文档还是人审的，但 AI 先把证据链给你摆齐了，你只需要做判断。

如果你也在和 GMP 文档较劲，非常推荐在本地把它跑起来试试，效果会比你想象的好。文档、密钥、审核过程全部留在自己手里，配合本地模型就是彻底的内网闭环。也欢迎来仓库里提意见，反正，多一个趁手的工具总不是坏事。
